### Step 2b — Game fixes from the owner (24 Nov 2026)

**Anti-abuse: the server is the referee** (owner, 25 Nov 2026). Players will try reload, exit, minimise, a second tab or a second account to gain time or see answers. The rules below apply to the quiz, duels and sudden death. They are built with security pack 2 and questions option B.

Today (checked in code on 25 Nov):
- A round's questions are fixed per room in `question_assignments`, so a reload does **not** re-roll them. That part is good.
- The timer and "question opened at" come from the **player's device** (`QuizScreen`, `useQuiz`). A reload shows the same question with a fresh 15″.
- All correct answers are in the site code.

| # | What a player does | What happens today | Rule (logic) |
|---|---|---|---|
| A1 | Reloads or closes mid-question to get a fresh 15″ | The timer restarts | The server records `served_at` the first time it sends a question to that player. Time = server now − `served_at`. A reload shows the **same** question with the **remaining** time; if time is up, the question is lost (0 points) and the next one appears |
| A2 | Opens the question, leaves, looks the answer up, comes back | Fresh 15″ | Same as A1: the clock never pauses once the question was served |
| A3 | Minimises the app or switches tabs to freeze the timer | On a phone the timer freezes | The countdown on screen is computed from the deadline. The server rejects late answers (+2″ grace for the network) |
| A4 | Changes the device clock | Response time is measured on the device | Only server time counts |
| A5 | Reads the answers from the site code or network | All correct answers are in the code | The server sends only the question and options. It checks the answer and returns right/wrong only after the answer (option B) |
| A6 | Answers the same question from two tabs or devices | Depends on timing | One answer per player per question (unique key): the first one wins, the rest are ignored |
| A7 | Leaves the round when it goes badly, to "restart" it | Unclear | A round never restarts. Answered questions stay. A question left half-way is lost (A1). Questions not yet served stay open, so the player can continue later. Leaving **between** questions acts as a pause and gains no information |
| A8 | Plays first with a second account (incognito) to learn the questions, then plays with the main one | Every player in the room gets the same 10 questions | Each player gets their **own** draw from the same categories. Optionally, new players can't join once a round is open (owner decision) |
| A9 | Duel: looks at the question and then declines, or leaves mid-duel | Not checked | The question is sent only after **both** accept. Leaving mid-duel: the clock keeps running and an unanswered question is lost. Declined duels are recorded as "never happened" (Step 2b) |
| A10 | Sudden death or tie vote: leaves to block it, or votes twice | The client decides parts of it | The server closes it at the deadline with whatever answers it has. One vote per player |
| A11 | A genuine network drop | Same as A1 | +2″ grace. On reconnect the player sees the remaining time. No pause, the same for everyone |

**Decision for the owner:** A7 lets a player pause **between** questions (they can get up, the party goes on, and they gain nothing from it). The alternative is one deadline for the whole round (10 × 15″ + reading time), stricter but harsh at a party. **Recommended: pause between questions only.**

### Step 3b — Quiz questions per year (Dec–Feb) — owner chose option B (24 Nov)
**Today (24 Nov 2026):**
- The bank holds 402 questions (the file is called "500"), all in EN and EL, and it ships inside the site code.
- Each round of 10 is drawn from fixed categories. **4 of the 10 always come from the category `'2026'`.** The `'2025'` category (40 questions) is never drawn.
- 47 questions (12 %) are about Greece. 26 of the 2026 questions are worded as a future event.
- Adding a question means editing the JSON and writing a migration. Once, a mismatch between the two zeroed scores (062).

**Target: questions picked by the game year, not by a literal year.**
- Each question carries: `topic` (history, trivia, lyrics, records, geography, staging, contest), `contest_year` (empty = evergreen), `audience` (all / Greek), `status` (active, retired), `valid_until` (for time-sensitive wording).
- A round is built from relative slots:
  - 3 from the **game year's contest**: line-up, host city, songs.
  - 1 from the **previous contest**: results.
  - 6 evergreen: history 2, trivia 2, lyrics 1, wildcard 1.
  - At most 1 Greek-audience question per round. A Greek-language room may get 2.
- When a contest is archived, its questions move to "previous contest". Next year they become history or are retired. Nothing is renamed by hand.

## Principle — Featured contest (agreed with owner, 19 Nov 2026)

**Source of truth: the CMS.** Each new contest's facts (year, city, host country,
dates) are stored in the CMS, either by the owner by hand or by Claude on the
owner's command. One contest is marked as the **featured** one and stands out in
the CMS.

**What it drives: the public pages outside the game, in EN and EL.**
- Homepage
- `/eurovision-night`
- The "When is Eurovision {year}?" content
- `/eurovision-predictions`
- Any other public evergreen page that mentions the current contest

**What it does not touch:**
- The rooms (game screens).
- The per-contest pages (e.g. `/eurovision-2026`). These are the finished,
  archived contests and stay as they are.

**SEO metadata follows it too.** Titles, meta descriptions, OG/Twitter tags,
H1s and structured data on those pages are generated from the featured contest.
They are never typed per page.

**When the featured contest changes.** It changes **only when the owner adds a
new contest**. Archiving a contest does not change what the public pages show:
the archived contest stays featured until the next one is added.

**Before the line-up is announced.** The pages show "Not announced yet" /
"Δεν έχουν ακόμα ανακοινωθεί". In place of the line-up they list every country
that has ever competed, from the data, never an empty table.

**Adding the line-up.** The owner enters entries by hand in the new contest in
the CMS, or asks Claude in chat to add what is known. The parser cron remains
the automatic route.

**Evergreen content rule.** Copy must stay true year after year without
rewrites. Counts and ranges come from data, not typed text: "since 1956",
"70 grand finals (1956–2026; 2020 cancelled)", the number of countries. The
first example is the "What is Eurovision trivia?" paragraph.

**No relative-time words.** Words such as "this year's contest", "φέτος",
"tonight", "απόψε", "next year" and "upcoming" go stale as the calendar moves.
Copy names the featured contest explicitly (e.g. "Eurovision 2027 · Burgas"), or
its wording comes from the contest's real state and dates. Examples found:
- `/past-contests`: "This year's contest: Eurovision 2026 →".
- Home kicker: "Tonight live" shown in November.

A first grep found such wording in public copy in `en.json`, `el.json`,
`predictionsText.ts`, `hubCopy.ts`, `archiveCopy.ts` and `archive.tsx`.
`/past-contests` also belongs on the list of affected public pages: its link
points to the featured contest, and its counts ("70 contests") come from the
data. Audit every public
page in both languages for hard-coded years, cities and counts.

**Status (19 Nov 2026): built.**
- The featured contest is the newest one (`siteYear.ts`), and `site.json`

## Principle — The owner drives the game phases (owner, 19 Nov 2026)

## Track 1 — Rethink flows

The full contest year from the owner's seat, one admin step per stage:

1. **New contest:** create the year (city, dates, host). It becomes the site's headline year.
2. **Getting participants:** the parser cron loads the line-up when it is announced. Manual edit stays possible.
3. **Testing / simulating:** test rooms with simulated or manual results, repeatable, invisible to the public site and to the real scoreboards.
4. **Night of Eurovision:** live results from the parser, with fallback to manual entry.
5. **Finalizing results:** score every room from the official ranking. Repeatable until closed.
6. **Closing / ending the contest:** results locked, no new rooms.
7. **Archiving:** the year moves to the archive pages, indexable.
8. **Creating the next contest:** back to step 1.

**Open questions for the owner, asked one at a time:**
- Who tests, and with what results?
- What must stay hidden while testing?
- Is "close" the same moment as "archive"?
- What do players see between contests?

**Deliverable:** a flow spec and a state diagram, then the DB, admin and site changes.

**Parse confirmation (owner request, 19 Nov 2026).** After every participants
or results parse, the owner sees a report of what was found and written: one row
per country with flag, country, artist and song, plus what changed since the
previous run (added, removed, changed). Warnings cover:
- an empty artist or song
- an unknown country
- a count different from what is expected

The parse can find three kinds of rows: past contests' entries, the general
line-up before the semi-finals, and semi-final and final line-ups, each with its
own link. The report shows which source and stage each row came from. It flags
rows that belong to another year or to the wrong stage. It never mixes them into
the featured contest.

**Predictions gate (checked 19 Nov 2026).** Predictions open only after the
participants parse: rooms in `pre_night` flip to `predictions_open` when
`parse_jobs` participants turns `done` (migration 030). A room that leaves the
lobby after that goes straight to predictions (067). The gate is "the parse
ran". It does not check that the parse found a real grand-final line-up. Proof:
on 19 Nov 2026 the 2027 parse finished `done` with 35 countries, all marked
`in_final`, and no artist or song. That is the general list, not the
finalists. No 2027 room exists, because new rooms play 2026 (078), so nothing
broke. Fix: predictions open only on the owner's **Open predictions** button
(see "The owner drives the game phases"). The parse write rule below blocks an
incomplete line-up.

**Write rule (owner's choice C, 19 Nov 2026).** A parse writes straight to
the game data, so the owner can re-run it many times while testing. It is
**blocked, with nothing written**, when it finds any of these:
- an empty artist or song
- an unknown country
- a finalist count outside 20–27

Either way the owner sees the report. Since predictions open only on the
owner's button, the owner checks the report before anyone plays. This replaces
the earlier idea of staging every parse until an Approve.

**Parser page year (fixed 19 Nov 2026).** The admin Parser page used to open
on the newest year in `parse_jobs` (2027 once that contest was created), while
Manual ranking used the game year (2026). The page now opens on the game year
and has a year picker. Parse, manual ranking and Finalize all act on the
picked year.

Superseded: the parse is staged first and goes live only on the owner's **Approve**.
Today the admin shows only "Last run: N rows". A no-write Test exists. The
entries are visible only under Contests → Edit.
